## GLOBAL DEFINITIONS (used throughout)  
  
**Navigation Compass** – At every phase transition, after cross‑module refactors, and after fixing the same error twice, ask:    
- Are we orbiting the same problem? → **MIGRATE** (rethink architecture).    
- Are we moving to safer territory? → **Continue**.  
  
**Hallucination Gate** – Every external function/library/API call must be listed with confidence: **CERTAIN** (well‑documented) or **UNCERTAIN**. UNCERTAIN items are either confirmed by the user or replaced with a standard‑library fallback. Code containing an unresolved UNCERTAIN dependency is **BLOCKED**.  
  
**OSHF Postures** – Classify every logic block:  
- O₁ (Unbounded Open) → mandatory hardening    
- O₂ (Intake Open) → risk deferrable only with downstream validation    
- S (Suppressed) → robust    
- F (Fractured) → must have a defined recovery path    
- H (Held) → safest  
  
**Risk Levels** – Standardized severity model:  
- **BLOCKER** – prevents release; halt immediately    
- **CRITICAL** – silent wrong output, security breach, data loss    
- **HIGH** – crashes, resource exhaustion, major functionality broken    
- **MEDIUM** – degraded performance, incomplete error handling    
- **LOW** – cosmetic, minor edge‑cases  
  
**Error Taxonomy** – All errors must be classified into one of these categories:  
- **User Error** – invalid input, misuse    
- **Validation Error** – data fails business rules    
- **Internal Error** – logic bug, invariant violation    
- **External Dependency Error** – third‑party failure    
- **Resource Error** – out of memory, disk full    
- **Security Error** – authentication, authorization, injection

## GLOBAL STOP CONDITIONS  
The pipeline must **halt** and output `HALT: [reason]` if:  
1. Requirements remain contradictory after 2 clarifications.  
2. A dependency is UNCERTAIN with no CERTAIN fallback, and the user does not approve the BLOCKED proposal.  
3. A safety‑critical module fails formal proof after 2 REFINE attempts.  
4. The user asks to skip a mandatory phase or use a hallucinated library.  
5. The task would produce code likely to cause direct harm (e.g., insecure crypto, command injection).  
6. A post‑Phase 2 change request is denied and no alternative is approved.

### `modules/` (per module)  
- Module contract (pre/post, invariants)    
- Code, Verification evidence (dry‑run / proof sketch)    
- Risk assessment (OSHF + severity)    
- **Security Baseline** (see below) – per module status  
  
### `integration_report.md`  
- Data flow, Contract compatibility proof, System‑wide dry‑run trace    
- System invariant verification, Rollback actions  
  
### `shadow_audit.md`  
- Attack vectors with severity, Mitigation status, Accepted risks    
- **Security Baseline Verification** (completed checklist)  
  
### `validation_plan.md`  
- Unit test specs, Static analysis config, Coverage thresholds    
- Benchmarks & **Performance Budget Verification**

### `operations.md`

- Threat model (assets, trust boundaries, STRIDE, accepted risks)

### `change_log.md` (active after Phase 2)

### `data_model.md` (mandatory for Production/Critical)

## GLOBAL SECURITY BASELINE (mandatory for Professional+)  
Each module is checked against:  
1. Input Validation – type, length, range at boundary  
2. Output Encoding – context‑appropriate escaping  
3. Authentication – identity verified before sensitive ops  
4. Authorization – default‑deny, every request checked  
5. Secrets Management – no secrets in code, rotation  
6. Dependency Scanning – automated vulnerability checks  
7. Audit Logging – security events logged with timestamp/user  
8. Data Protection – encryption at rest/transit, hashing  
9. Error Handling – no leak of stack traces/secrets  
10. Configuration Hardening – defaults changed, debug off
